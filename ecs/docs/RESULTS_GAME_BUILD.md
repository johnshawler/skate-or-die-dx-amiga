# Results of the game build (executable + data folder) on the 68020 / AGA / 2 MB Chip model

Status: **performance target met for four of the five events; Joust holds its pace but with 12% instead of 20% headroom on the mean (re-measured with the final build, including INTER: mean 54.7 ms of a 62.5 ms slot, median 50.6 ms = 19%, p95 57.2, 1.7% of passes over their slot; the earlier 16-18% figures were not from this metric).** The original's event/competition driver (INTER) now runs inside the game: practice-again prompt, turn-taking, results screens, competition in all events. Nothing here was run on a real Amiga.

## What exists (`ecs/game`, product in `ecs/game/dist` after `./build.sh`)
* `SkateOrDie` (19.6 KB) + `data/` (7.0 MB: title/shop/map/score screens, font, skater sprites, ADPCM title song, shop song, per-event memory image `evN.pak`, per-event song `evN.raw`, effects `sfx.raw`, and the five event overlays `ramp/hj/race/jam/joust.ovl`). The program finds its data through `PROGDIR:data/`; the HDF (`tools/mkhdf.sh`) is only a carrier.
* Event code = the original 65816 overlays translated to C (`tools/t816`, `tools/gen_ecs.py`), native replacements for the hot routines (`native/`), a platform layer (`src/evrun.c`, `platform.h`, `os.h`) and the picture conversion `src/c2p.h`. Only one event is in memory at a time (loaded with `LoadSeg`).
* Machine: A1200 class (68020 at 14.19 MHz assumed), AGA, PAL 50 Hz, 320x200x16, 2 MB Chip, **no Fast RAM**, Kickstart 3.1. Tested in FS-UAE 3.1.66 with `uae_cpu_memory_cycle_exact` (UAE's model of CPU/chip-bus timing).

## What was done to get here (all verified, none of it lowers fidelity)
All natives and generator changes were checked against the original machine code: `tools/nativetest.py` (native routine vs the original on real game states: ramp/HJ/joust/race/jam, 40-200 samples each, 0 differences), `tools/lockstep_ecs.py` (whole overlay, translated vs original on the oracle, memory banks, registers, write log hash and picture: identical for all five events), `tools/c2ptest.py` (68020 conversion kernels run in Unicorn against a first-principles reference, 4 variants x 300 random rounds, 0 wrong).
* Natives added for the recolour loop (ramp, HJ, joust), the joystick/paddle routine (ramp, HJ, jam, race, joust), the text glyph (jam, race), faster rectangle push; direct word reads/writes for known banks; indexed accesses with a known bank compiled as direct loads (`tools/emit_ecs.py`); 256 KB conversion table for race and joust (2-14% of a pass; the jam has no memory for it); shorter paddle timers (same decisions); pacing against CIA time-of-day.
* Tried and dropped (measured slower or no gain): a 16-pixel-at-a-time conversion kernel (the loop no longer fits the 020's 256-byte instruction cache), 64-bit bitplane fetch, `-Os` (-25%), `-O3` (same), bank 3 pointer in a register (same).
* Sampling profiler (`-DPROFILE_PC`, `tools/run_prof.sh`, `analyze_pf.py`) found the real costs; the machine is bound by Chip-RAM accesses and instruction fetches, not by instruction counts.

## Practice prompt, competition, competition in all events (new; `tools/intertest.py`, FS-UAE runs)
The original runs these through INTER (bank 7 `$6800-$7FFF`: `$692D` start of an event for a player, `$7578` end of an event, the text-mode screens at `$E0:0400`). Its 1,168 instructions are translated like the events (`cfg/inter.json`, prefix `i_`) and linked into every overlay; the only parts replaced are the ProDOS file calls (`$73B4`: the data are in the event images), the scene runner (`$6F7C`, see gaps) and the 1.4 s wait (`$7755`, native: waits 1.4 s or a key or the button).
* **Translation check:** `tools/intertest.py <players> <practice> <compete_all> <first event> <seed> [keys]` runs INTER on the 65816 oracle and the translated code with the events faked (a random score at every `$031000`), comparing bank 7, the text page at every stop and at every key wait. Identical in all scenarios tried: 1 player practice (YES/NO answers), 3 players in one event, 3 and 5 players in all events.
* **Platform side:** INTER's text page is drawn with the shop font (white on black; `$9E`, INTER's YES/NO marker, as a small arrow); joystick left/right and the cursor keys are INTER's arrow keys, Return/space/button confirm, `y`/`n` answer directly; ESC in an event or in a text screen sets INTER's own quit flag (`$7E19`) and INTER takes its quit path back to the shop. A competition in all events moves from one event overlay to the next by saving INTER's 6 KB state in the shop's memory (`Menu.inter`). In the two-player events the second skater is the next player (or the computer) as in the original.
* **Seen working in FS-UAE (test build with `DEBUG_KEYS`, F6 ends the event as if over, F7/F8 sign up three players and compete in the ramp / in all events):** practice YES restarts the event and NO returns to the shop; three players take turns in the ramp with the "NEXT SKATER" screen between them and a results screen ("SCORES FOR RAMP ... OVERALL"); competing in all events went ramp -> high jump -> downhill -> jam (pairs) -> joust (WIN/LOSS) with the results screen of each, then back to the shop; ESC mid-event and ESC on a results screen return to the shop; Rodney's "CONGRATS <name> YER TOP SKATER!!!" shows for the player with the most points.
* **Fixed on the way:** Rodney stayed silent after every return from an event (the shop's speech state was not reset the way the original's fresh overlay load does); `__builtin_setjmp` corrupted the display on the Amiga build (it uses the frame pointer register the translator reserves), replaced by a small assembly setjmp.

## What the original does after a competition (checked in the disassembly, then ported)
The question "ceremony scenes, high-score name entry, scene pictures from disk" turned out to rest on a wrong reading of mine; what the code really does:
* **INTER's scene runner (`$6F7C`)** only loads files (and LZW-unpacks them into memory banks; the runner contains no drawing code). The script per event (`$6A68`, file numbers of the original disk): ramp F1-F7, high jump F1-F6 + F8, race F9, F2, F10-F15, jam F16, F2, F17-F21, joust F22, F23, F2, F24-F28 (F2 is the font; F1, F22, F23 are 32 KB pictures that go into a memory bank for the event to draw), and for "back to the map" (both when a single event ends and when a competition in all events is over) F29-F33 (the shop pictures: map, Rodney, sign-up list, scores, board), F2, `highs`, F35-F39 (the shop/map code). The loaded data are what the event memory images (`evN.pak`) and the shop assets already hold; so there are no extra "ceremony scenes" or winner pictures to port. What a player sees after a competition is INTER's results text screens, F39's High Scores screen with the new entries, and Rodney's congratulation: all now in.
* **No typed high-score name entry exists.** F39's start-up code (`$1B5A` -> `$1414`, `$1495`, `$1538`, `$1B9D`) compares each player's best scores of the first four events with the 12-entry table, inserts new ones (shifting the others down, the name copied from the sign-up list, the entry shown once in its own colour), sets the request that shows the High Scores screen first, and writes the table (`/sod/highs`). That update was **missing from my port** (the table never changed): now ported (`menu_hs_*` in `src/menu.h`), the table is saved to `data/highs.bin` when it changes and read at start-up, and INTER's final player order (sorted by results), points and best-score tables are handed back to the shop (`$6810`, `$68EE`, `$68FE`, `$68A8`, `$68E2`, `$68DA`).
* **Check:** `tools/hstest.py` runs F39's start-up routine on the 65816 oracle and `menu_hs_update` on random players, results and tables (1,600 trials, 1,388 with new high scores): identical. In FS-UAE (test keys) three players in the ramp: results screen, then the High Scores screen with the three new entries (highlighted), `data/highs.bin` written (192 bytes), Rodney's congratulation after it for compete-all.
* The saving uses `PROGDIR:data/highs.bin`; the original's disk file is replaced by it. Not checked: a second session reading the file back on the emulator (the reading code is 6 lines; the file contents were checked).

## Downhill Jam 20% faster (12 passes a second instead of the original's 10)
* **Why it was slow:** the sampling profile (`-DPROFILE_PC`, 90 s of stress input, unpaced) put 46% of the time in the picture-conversion loop and 19% in the background copy. The jam scrolls a 168-row window of its picture ($3400-$9CFF) by whole rows; every pass the copy rewrote the whole window and marked it all changed, and the converter then compared all 6,720 groups with its shadow copy (30 ms a pass even when nothing had moved: conversion alone was 38 ms of a 75 ms pass).
* **What was measured about the scroll** (original code on the oracle, practice, waggle input): the offset moves by 0, 1 or 2 whole rows per pass (a jump back when the strip wraps); with the shift taken into account about 77 of 8,000 groups differ from the previous pass, against 872 (2,639 on the passes that scroll) when compared in place.
* **The change** (`native/dh_engine.h` `bg_fill_scroll`, `src/c2p.h` `C2P_SCROLL`, jam only): the copy compares each new row with the old row of bank E1 that has scrolled to its place, writes only what must be written (everything when the window moves, only changed rows when it does not), and marks only the groups that differ; `rt_scroll` shifts the converter's pending spans with the picture and records the shift; the converter shifts the planar picture of the buffer by the scroll (one `movem` copy) and converts only the marked groups, with no shadow copy. A first fill, a jump of the offset or an event restart marks everything. Memory (bank E1 and bank 1) is written exactly as before.
* **Checks:** `tools/lockstep_ecs.py ev21` (translated overlay with natives against the original, all banks, registers, state at every pass): identical for 1,200 / 3,000 / 2,500 passes (waggle, random, two players); the same run converts the picture the way the platform does (`tools/c2p_host.c`, the same `c2p.h`, two buffers, collect / convert / swap) and compares it with a conversion of the whole picture after every pass: 0 differing passes. Breaking the planar shift, or the span shift, on purpose makes that check fail within about 100 passes (so it does test the new code). On the A1200 model a `C2P_VERIFY` build compared the real 68020 conversion with a full conversion after every pass: 461 passes of stress play, 0 differing bytes.
* **Result** (FS-UAE A1200 model, 240 s of stress input, paced; before in brackets): at the old pace of 10/s the mean work per pass fell from 75.3 to 56.7 ms (picture conversion 38.4 to 9.8 ms). At 12/s: mean 55.6 ms (slot 83.3 ms, **headroom 33%**, contract 20%), p95 80.0, p99 96.2, 4.8% of the passes over their slot (5.2% before at 10/s); the counter shows 12 / 11 / 12 (now / lowest second / average). The game clock and everything else in the jam now run 20% faster than the original and than the NES-rate comparison made earlier.
* **Not done / caveats:** the other four events are unchanged (the race has the same background copy and could get the same treatment; not asked for). Free Chip RAM during play was not re-measured. The pass count in the verify run is small and I did not count how many of its passes scrolled. A human has not yet played the new build to check that the faster jam still feels right.

## Matching the NES version's speed (race, jam, map)
You asked for the speed of the NES version. Measured on the NES ROM in FCEUX (60 frames a second, scripts in `tools/speed/`) and on the original code on the oracle:
* **Map (shop door to the wall below it):** NES about 67 frames, original code 57 passes -> 50.3 passes a second needed. **Done: 50 passes a second** (`MAP_HZ` in `ow.c`, one a frame; it was 25, an estimate of the original's rate). The sign and fountain animations stay at 25 a second.
* **Downhill race, coasting from the start:** NES scrolls 0.355 px a frame = 21.3 px/s; the original code moves exactly 1 px a pass -> 21.3 passes a second needed (the START sign has the same size in pixels in both versions). **Done: 21 passes a second** (it was 11).
* **Downhill jam:** NES scrolls about 27 px/s whatever the input (0.46 px a frame). In the original code the camera follows the midpoint of the two skaters (at most 4 rows a pass, `$26F6`); a skater's position advances one row each time a speed accumulator overflows (`$2567`-`$2577`, `INC $6464,X` in `$25B9`, also called by the two boost steps `$2AB0`/`$2ABF`), and the speed comes from pushing: coasting 0.25 rows a pass, a synthetic waggle 0.32 on average, full effort 2 (the course is 1,872 rows long, the jam 2 minutes). So the original at its own 10 passes a second is 2.5 px/s coasting, about 3 on my synthetic waggle and 20 at full effort, against the NES's constant 27: no pass rate gets the coasting speed there (about 110 a second). **Tried, as you asked:** `nat_step_pos` (`native/dh_engine.h`, `N_STEP_K` in `dh21_consts.h`) makes a skater advance 2 rows each time the original advances 1 (the original already moves up to 2 rows a pass; the two skaters, the boost steps and the camera cap of 4 are covered by this), and the jam runs at 14 passes a second. Speeds now: coasting 7 px/s, my synthetic waggle about 9, full effort 56 (the NES: 27, constant). **Whether this feels right is for you to say**: `N_STEP_K` and the pace in `evrun.c` are the two numbers to change (a speed of more than 4 rows a pass needs the camera's cap at `$2704` raised too, so 2 is the largest step I tried). The clocks stay pass-driven as you decided: at 14 passes a second the jam clock runs 1.4 times real time, the race clock 2.1 times.
* **Jam tile drawing:** the passes that draw a new row of scenery tiles (40 calls of `$483A`) were 80-130 ms; `nat_tile` does the call natively (same bank-2 writes, stack bytes, registers and flags), which brought the passes over their slot at 14/s from 9.0% to 6.0%.
* **The clocks are pass-driven in the original** (race: 10 passes a displayed second; jam: also 10, seen on the oracle). At 21 passes a second the race clock runs about 1.9 times real time (after about 2.5 minutes of play it read 4:33) and the jam clock 1.2 times; the NES clocks run in real time. Scores that use the clock stay as the original code computes them. Whether to make the clocks real-time (changes the game's time/score arithmetic) is open.
* **How the race got cheap enough** (same engine in the jam): the per-pass copy of the scrolled picture into banks 1/E1 and the full comparison of it were the biggest cost (the profile put 49% of the race's time in that copy). The copy is not made any more: bank 1/E1 window rows are never read back (checked on the write log and by the lockstep, which now never compares them), everything that is drawn into the picture is drawn into bank 2 before the copy and not after (checked), so the platform converts the window straight from bank 2 (`rt_win_src`) and the changed groups are the ones written into bank 2 since the last pass (`rt_b2min/rt_b2max`, kept by every store to bank 2 in these two overlays, the blits and the restore), at the row the window now has; a scroll by whole rows shifts the planar picture. Mean work per pass: race 57.1 -> 39.1 (scroll-aware compare) -> **26.0 ms**; jam 75.3 -> 55.6 -> **44.2 ms** (the jam's sprites are many and wide: its conversion, 13 ms, is now the largest part and has coarse spans; a per-row bit mask of changed groups would cut it).
* **Lockstep note:** for the jam the oracle is given the same position step at `$25B9` (`tools/lockstep_ecs.py`), so "identical" means the port equals the original plus that one deliberate change; the plain original is no longer what the jam is compared with.
* **Checks:** the host lockstep (translated overlays with natives against the original; all banks except the unmaintained window of banks 1/E1; every pass the platform's planar picture, built from the translated memory, against a conversion of the **original's own picture at the same pass**): identical for the jam (1,200 waggle, 2,500 random 2-player, 3,000 waggle 2-player passes; again after the position step and the tile native: 1,200 / 2,500 / 3,000 / 1,500) and the race (1,200 waggle, 1,500 random); breaking the blit/restore marking or the plain-store marking makes it fail (so both are exercised). On the A1200 model a `C2P_VERIFY` build compared the real 68020 conversion with a full conversion after every pass: race 541 passes, jam 399 passes, 0 differing bytes. The race at 21/s: 25.0 ms mean in a 47.6 ms slot (47% headroom), p99 34.9, 0.3% of the passes over.
* **Not done / caveats:** the jam is not at the NES's speed (above); the clocks (above); the ramp, high jump and joust were not touched and not compared with the NES; the speed comparison uses the NES's scroll against the original's scroll in pixels (same size of the scenery in the race; the map is drawn at a different scale in the two versions, so the map comparison is by the time to cross the same stretch); free Chip RAM and the on-screen counter at the new paces were not re-read; a human has not played these builds.

## "SKATING TO ..." screens, and the Jam's scroll (latest)
* **The screens.** The original shows INTER's text screen "SKATING TO <event>" (names from INTER's table at `$7BC3`: RAMP, HIGH JUMP, DOWNHILL, JAM, POOL JOUST; "SKATING TO " at `$7B29`, the code at `$7518`) while the next event loads, and "SKATING TO SKATESHOP" at the end; the port ran INTER's code but the screen was never on long enough to see. Now `ow.c` (`sk_draw`, `sk_wait_fire`) shows it before every event, in INTER's text style (white on black, the shop font): the title, the event's name, **the event's controls from the manual** (`sk_ramp`, `sk_hj`, `sk_race`, `sk_jam`, `sk_joust`: the ramp's trick table with the pumps and the lean, the high jump's speed and timing, the race's REGULAR / GOOFY foot, jump / duck / slide turn, the jam's punch / kick with high / middle / low and the second player's keys, the joust's rules), the controller and button, and **"PRESS FIRE TO START"**. The game does not start until a player presses fire (the joystick in either port, Space, Return or Shift); the button that brought the skater to the exit has to be let go first; ESC goes back to the shop. The screen stays up while the event's files load. In a competition in all events it comes before each next event. "SKATING TO SKATESHOP" comes when the event is over (1.5 s, and while the shop's files load). `tools/lint_screens.py` checks that every line fits the 40-column text page.
* **Checked** on the A1200 model: each of the five events' screens (screenshots), the fire press starting the event (race, jam), ESC out of an event giving "SKATING TO SKATESHOP" and then the shop, a three-player competition showing the screens between events. **Not checked:** the joystick's fire button itself (only Space was pressed), the screens on an NTSC machine, the WHDLoad build (not rebuilt).
* **The Jam's scroll.** The camera follows the middle between the two skaters and moved at most 4 rows a pass (`CMP #5 / LDA #4` at `$26F6`); with the skaters now moving up to 6 rows a pass (my probe on the waggle input: steps of 6, the camera's target up to 3 rows ahead of the camera) they could run ahead of it. `nat_camera` (`native/dh_engine.h`, `N_CAM_CAP` 7 in `dh21_consts.h`, 7 being the most the scroll routine at `$48B3` has a step for) lets the camera move up to 7 rows a pass: the target is now never ahead of the camera (probe: 0), the camera steps up to 5. Lockstep (the oracle gets the same step and the same camera) identical for 3,000 waggle / random passes (1 and 2 players) and the probe runs; A1200 timing unchanged (14/s: mean 45.6 ms, p95 72.2, 6.1% over the slot). The skater's distance from the camera is still the game's own: up to about 60 rows, within the 168 rows of the window.

## Jam camera follows the leader; the Amiga credit on the title screen (latest)
* **Scroll outpaced at full speed.** The camera follows the middle between the two skaters, so a skater at full speed runs ahead of it at half its own speed until the game's own limit (about 60 rows) is reached: the skater slides down the screen faster than the scroll (at the doubled step this takes about 3 s). `nat_camera` now also keeps the leading skater within `N_CAM_LEAD` = 40 rows of the camera (`dh21_consts.h`), so the scroll follows the leader at up to 7 rows a pass (the skaters move up to 6, 8 on a boost step); the middle still rules while the skaters are close (gap under 80). Probe over 3,000 passes: leader at most 44 rows ahead of the camera (was up to 61, growing with the speed), the camera's target never ahead of it. The price: the trailing skater is up to about 80 rows behind the camera (was 60), so at the game's largest gap it is at the top edge of the picture. `N_CAM_LEAD` is the knob (smaller keeps the leader closer, the trailer further up). Lockstep identical (the oracle gets the same camera) for waggle and random input, 1 player against the computer (the two-player runs do not scroll without both buttons); A1200: mean 45.4 ms at 14/s (slot 71.4, 36% headroom), p95 71.9, 5.6% of the passes over.
* **Title screen.** The credit list (picture F52) has one more bullet, "AMIGA VERSION BY BOATOFCAR", in the list's own font (letters cut from the list; the Y, which the list has no letter for, is drawn like its V with a stem). The IIGS block moved up five rows to make room (`tools/title_credit.py` makes `data/title.scr` from `assets/title_orig.scr` at every build). Seen on the A1200 model.

## WHDLoad install (latest)
`build_whd.sh` builds `dist_whd/SkateOrDie/` (`SkateOrDie.slave` and `data/` with the program image, the five `.ovx` overlays and the data files); `tools/mkhdf_whd.sh` makes a test HDF (the WHDLoad executable is not part of the product). Slave credits as you chose: name "Skate or Die", copyright "(c)1988 Electronic Arts", info "Amiga version by Boatofcar" with the requirements. **Memory:** the slave asks WHDLoad for 2 MB of expansion memory and 1.5 MB of Chip; with exactly 2 MB of Fast RAM WHDLoad itself reports "Can't allocate ExpMem" (it needs memory of its own), so the requirement is stated as **4 MB Fast RAM**. **Tested** (FS-UAE A1200 model, WHDLoad 18.0, 4 MB Fast): test builds (debug keys and an automatic walk) went from the shop through the map into the ramp, high jump, race, jam and joust, with the "SKATING TO ..." screens, fire starting the event, and ESC out through "SKATING TO SKATESHOP" to the shop; the final install booted to the title (with the new credit) and the shop. **Not tested:** real hardware, a real joystick button, NTSC, the high-score file under WHDLoad (`resload_SaveFile`), a full competition under WHDLoad. The ramp "stall" I noted in the first WHDLoad try was the ramp waiting for the button, as it does in the normal build. The test builds of the slave had needed one fix (a debug-only file write that the OS-free build cannot do).

## Not verified / known gaps
* Synthetic waggle input, practice mode against the computer opponent; not the source corpus replays; the competition runs above used F6 (event ended by a key, with pseudo-random scores) rather than real play in each event, three players only; two-player play inside the events was not exercised by a human; no name entry run (sign-up name entry is the earlier port of F39; the original has no separate high-score name entry); the timing runs entered events with test keys F1-F5 (compiled out of the product build with `DEBUG_KEYS`); the map-walk check above used synthetic input inside the events; 
* FS-UAE's timing is a model; real A1200 timing, chip-bus contention and the audio under load are unmeasured. The 14.19 MHz clock is an assumption.
* Joust headroom 12%; Jam: 4.8% of the passes over their slot at 12/s (the scrolling passes).
* Kickstart 1.3 in `roms/` is Guardian-patched and cannot run AGA; the IIGS ROM and disk image are not in the repository (`docs/briefs/ROM-Locations-Brief.md`).
